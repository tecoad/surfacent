# Surfacent

See README.md for the architecture. Key rules:

- **TypeScript only, never JavaScript.** No `.js`, `.mjs`, `.cjs` or `.jsx` files, including configs and scripts. Core, the MCP server and `packages/tool/*.ts` run in Node with native type stripping: erasable syntax only, `import type` for types, explicit `.ts` extensions on relative imports. Run `npm run typecheck` after changes.
- **No dead code.** `npm run lint` (oxlint, `.oxlintrc.json`) and `npm run knip` (`knip.json`) must pass: remove what they report instead of silencing it. They can't see a prop that's passed but never read, or styles injected for a component that's gone, so delete those with the code they belonged to. The React Compiler purity rules and `exhaustive-deps` are off for now: the toolbar's older code would need a refactor first.
- The tool is layered in **aspects** (surface, color, response, corners, density and text). Never special-case surface in the toolbar, plugin or prompts: add behavior to the aspect definition in `packages/core/src/aspects/` and let the registry drive the rest.
- Every intent is relative to its context: an element reads the nearest ancestor in the same aspect (`nestingChain()` in `packages/core/src/chain.ts`). Nothing renders a fixed color or size.
- `packages/tool` is licensed under PolyForm Shield: its `LICENSE` must stay, and so must the toolbar's part in `packages/surfacent/LICENSE`. New toolbar behavior goes in `packages/tool/src/design/`, plus small hooks in the toolbar, popup and output files.
- Only `packages/surfacent` is published (npm `surfacent`: `surfacent`, `surfacent/tailwind`, `surfacent/vite` and the `surfacent mcp` bin). tsup bundles the workspaces' sources into it. After changing an entry point or a dependency, run `npm run check:package`. Commits follow Conventional Commits, because `fix:` and `feat:` on `main` publish a release (CONTRIBUTING.md).

## Applying intents from the toolbar

Prompts from the toolbar (copied, or via the surfacent MCP tools in listening mode: `surfacent_listen`, then `surfacent_resolve` once applied) say things like `Set data-surface="raised" on this element` with a source location. Edit that JSX element: add the attribute, remove the classes the aspect now owns (listed in the prompt), and replace fixed neutral colors inside it with `text-ink*`, `border-edge`, `divide-edge`. Keep layout and spacing, radius unless the prompt sets `data-corner`, text sizes unless it sets `data-text`, and brand colors unless it sets `data-color`.

A suggestion request from `surfacent_listen` (the toolbar's suggestion mode) changes no code: propose intents with `surfacent_suggest`, following its `suggestionGuide`. Its texts live in the aspect definitions (`why`, `when`) and `packages/core/src/philosophy.ts`.

## UI and the playground

- The toolbar's UI is `packages/ui` (`surfacent-ui`): ui-sdk parts in a compact dark look, Tailwind v4. Before using ui-sdk, read `node_modules/@ui-sdk/react/docs/llms.txt`; to build a new component, also search `node_modules/@ui-sdk/react/docs/core.md` by heading and read `rendering.md`. Custom primitives are in `packages/ui/src/primitives/` (React parts in `parts.ts`). Tokens and the state variants (`hov:`, `fv:`, `act:`, `foc:`, `group-hov:`, `group-act:`) are in `packages/ui/src/styles.css`; they also match `data-force`, which the playground uses to pin states.
- New toolbar UI in `packages/tool` uses `surfacent-ui` and Tailwind classes, never new SCSS. Classes in `packages/tool/src` and `packages/ui/src` reach the toolbar's shadow root by themselves (`src/design/ui.css`, compiled by `styles.ts`: `surfacentSource()` from `dev.ts` in the demo, tsup in the package); restart the dev server after editing `vite.ts`, `dev.ts` or `styles.ts`. Toolbar elements that the page's pointer handlers must ignore carry `data-feedback-toolbar` (the dock passes it through `rootProps`).
- Scrolling regions in components use `ScrollArea` (edge fades, no scrollbar, no sideways scroll), never a bare `overflow-y-auto`; Select and Combobox lists pass `tabIndex={-1}`.
- Fixed colors are picked on the color strip (`ColorControl` without `onColorsChange`: `#/color` without +, `""` for Not set): an aspect's colors, the marker color. A color made of settings (an aspect's `colorFields`, like the accent) is one `HexRow`. On/off options are `ToggleRow` switches; modifiers that exclude one another (an aspect's `modifierGroups`, like the text's ink) are `Chips` under their own label, one on at most: pressing the one that's on clears it, since none is the default.
- Keep fields minimal: a field changed from what's saved or in source shows its label in blue (`modified` on the kit's rows, `data-modified` on a `labelText` label), with no Undo, no "changed" text and no line restating the value. Going back is a control's own job: the picker's menus, color strip and cycles start with Not set.
- Focus rings are keyboard-only (`fv:`, i.e. `:focus-visible`), so a click never leaves one; don't style `:focus` or `foc:` with a visible ring.
- Keep non-component exports (class strings, data) out of `.tsx` component files so Fast Refresh keeps working. `packages/ui/src/index.ts` re-exports every module: regenerate it when adding one.
- The playground is `apps/demo/src/playground/`: `registry.ts` lists the pages (sidebar order, prev/next); `pages/*.tsx` export one component per element, a `StatePage` with its `states` (or an `AreaPage`); `shell/` is the sidebar, the inset card and the states panel. The URL is `/playground/#/<page>/<state>`. Every state has a `code` example built with `snippet.ts` that prints what `render` shows (stage wrappers like `PanelFrame` aside), imports from `surfacent-ui`, and must compile: run `npm run check:snippets` after changing a page.
